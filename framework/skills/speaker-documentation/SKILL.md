# Speaker documentation

You turn the selected candidate's files into a standalone construction and performance package in `framework/projects/<slug>/final/`. Aim for a reader unfamiliar with the project to be able to build the speaker and understand what to expect from it. Every figure comes from a result file in the candidate's `sim/` folder or from the inventory; every plot is generated from those files. Use the results as the canonical behavior of the selected design.

The deliverable is one PDF, `final/<slug>-design-package.pdf`, assembled from the Markdown documents and images you write into `final/`. Keep the Markdown and images in `final/` next to the PDF; they are the editable source of the package.

**Write for the builder.** Everything in the PDF should help someone build the speaker, understand what to expect from it, or verify it. So it carries the drawings, the schematic, the plots, the parts and the assumptions and limits that change what a builder does or believes - in plain language, with a speaker name in the title. It does not carry the framework: no application versions or constants, no raw `model_notes` or `validity` blocks, no JSON paths or result-file citations, no candidate IDs, iteration logs or ranking history. Traceability does not suffer for it, because the `sim/` files and the evaluations already hold every figure's provenance and are what a later reader re-derives a curve from; the PDF is not where that lives. Manufacturer and independent measurement sources are a different matter and belong in the document, cited readably.

**Analysis and instructions only.** The user knows the simulations are the design basis. Include no simulation-versus-measurement disclaimers anywhere in the deliverable: title, body, captions, axes, legends, tables, footers or technical sheets. Do not write "this is simulated", "not measured", "not production-yield data", "not a certificate", "no claim is made" or substitute caveats with the same function. Present response, impedance, excursion and room behavior directly as results. Do not rename their provenance as laboratory measurements.

**Interpret every performance figure.** Add a concise, figure-specific description covering what the agent sees, what that means for this speaker, and the design or use implication. Tie the interpretation to visible features and the relevant engineering reference. A caption that just names curves, repeats a number or lists solver settings is insufficient. Keep units, drive, distance, reference band, channel correlation and geometry where they affect interpretation. Put numerical-validation and acquisition detail in the project's evaluations.

Examples of useful interpretation: "The branches meet with a small phase difference, so they reinforce through the handover; retain the shown polarity." "Excursion rises below the port tuning; reduce drive for strong content in that range." "Moving the seat reduces the bass variation; start with the illustrated placement." State the specific frequencies and levels from the actual case. Do not invent listening impressions or universal performance guarantees.

**Constructive does not mean hiding a miss.** Explain the cause, practical consequence and selected response to a weakness. Express sensitivity studies as operating or design tradeoffs: what changes, by how much, and what to retain or adjust. Express missing purchased-part dimensions as precise receiving/fit instructions, without fabricating a coordinate. No machine-talk, defensive boilerplate, raw result dumps or unexplained scores.

**Drawings first; useful analysis beside plots.** Prefer labelled views, dimension lines, machining schedules, parts tables and short bullet lists. Use numbered lists for assembly order. Use short paragraphs beside performance plots to explain the speaker behavior and the action it supports. Do not repeat drawing dimensions in long narrative instructions or hide essential machining information in prose.

Inputs: `project.json`, `reference/reference.json`, the selected `candidates/<cNN>/` (candidate.json, notes.md, sim/), the last evaluation, and the inventory records of the parts used. `framework/references/cabinet-geometry.md` and `framework/references/crossover-design.md` say what a construction document has to state about interior fit and about component ratings. `framework/references/baffle-and-driver-placement.md` and `framework/references/passive-radiators.md` say which placement figures a builder needs - driver heights, edge distances, centre-to-centre spacings, the panel each radiating surface is on and the wall distance that implies. `framework/references/target-response.md` says which response statistics to quote and how they differ from the published figures of a measured product. `framework/references/measurement-and-model-limits.md` supports the internal evidence review. Apply the canonical-results and analysis-only communication rules above to the builder package.

Tools (one command each, `.speaker-venv/bin/python`):

- Follow `cad-drawing` and [the CAD exporter contract](../../tools/cad-drawings.md) for fabrication PDF sheets, dimensioned millimetre DXFs and STEP parts/assembly. `framework/tools/cabinet_drawing.py` can still supply a preliminary elevation and cut list; use the required CAD workflow below for the final construction set.
- `framework/tools/schematic.py --input candidates/<cNN>/sim/crossover_network.params.json --out final/ --name crossover` for the schematic PNG, the connection table and a board netlist. Labels show reference, part name and specification; make sure every leaf in that parameter file carries `part` and `rating` before you draw it. Then open the rendered image: a grouped block is not a construction drawing, and document 2 says what it has to become.
- `framework/tools/build_pdf.py --out final/<slug>-design-package.pdf --title "<speaker name>" --subtitle "<one line>" --md final/README.md --md final/01-cabinet-construction.md ... --preview final/preview/` to assemble the PDF in reading order and render each page to a PNG for inspection. It supports headings, paragraphs, lists, tables, images and code blocks; images are referenced from the Markdown with relative paths.
- `framework/tools/plot_curves.py` for every performance plot (system and per-section SPL, acoustic section phase around crossovers, off-axis maps, impedance, excursion and port speed at the stress drive, reference comparison). Where a plot needs phase and the helper does not expose it, take it from the complex responses in the result files rather than reconstructing it.
- `framework/simulations/response_metrics/run.py` when a comparison statistic is missing.

## Required cabinet CAD workflow

**Use [cad-drawing](../cad-drawing/SKILL.md) for every cabinet drawing set and revision.** It owns the cabinet assembly/elevation/section drawings, driver placement, screw-hole patterns, machining details and all other construction geometry. Read its [sourced drawing reference](../../references/cad-drawing.md), then include its verified PDF sheets, editable CAD files and matching feature schedules in this package. A prose cut list or an illustrative cabinet sketch does not replace this workflow. Keep the electrical circuit schematic and its physical wiring documentation in the crossover workflow below.

## Freeze the realization before writing

Follow [the construction audit](references/construction-audit.md) for loose-panel datums, routed contours, joints, exact board parts, visible wiring and canonical phase plots. Reconcile inherited physical artifacts and prose using [comparable sources and revisions](../speaker-design/references/simulation-integrity.md). These procedures supplement the package contents below; a correct netlist or occupancy table alone is not a usable assembly drawing.

Use the selected stock realization as the single source for every physical leaf, bank, polarity and geometry datum. A late rating or stock change goes into the parameter files first, followed by network/board/whole-system replay and regenerated schematic, connection table, parts list and plots. Reconcile IDs, values and quantities across those artifacts, including the most stressed positions. A prose correction alone cannot update generated wiring.

Check the selected evaluation's inventory search review before releasing construction documents. An unexplained component bank, unavailable item or oversized/costly assembly calls for the [component research procedure](../speaker-design/references/component-research.md) and an affected-design replay, not a paragraph defending the restricted inventory. Keep search history in the project; the builder receives the selected exact parts and the assumptions that affect construction.

Record source provenance and robustness checks in the evaluation. Deliver a definite stock crossover, cabinet and assembly plan with performance analysis. Resolve source questions and margins during design, then explain the selected choices and practical implications in the package. Include a measurement procedure only when requested.

Quote wood dimensions separately from static assembled and moving/service envelopes. Include joints, fastener access, installed wiring/support reserves and internal versus total duct length. Keep the geometry audit and application provenance in the project; put the dimensions and assumptions a builder needs in the package.

Resolve cabinet construction and fitting to a single millimetre. Present wood dimensions in whole millimetres throughout drawings, cut lists and machining schedules; use centreline, symmetry, bolt-circle and angular constraints for derived coordinates. Define exact target sizes and mating stacks, not ranges or unspecified "fit/shim as needed" allowances. Do not add adhesive thickness to required dimensions or use glue to make up a dimensional gap: dimension dry wood contact. Where sealing tape or gaskets intervene, show their specified **compressed installed thickness** in the stack; free thickness is purchasing information, not the seating dimension. Specify any rigid spacer or stop separately. State the fitting tolerance and distinguish it from display precision; whole-millimetre labels do not make uncertain factory data accurate.

**Every cabinet dimension belongs visibly on a drawing.** The sheets must let a builder recreate the cabinet in CAD without measuring the picture, inferring an unlabelled feature or searching the narrative. Dimension all panels, thicknesses, joint angles/overlaps, driver placement, aperture profiles/radii, recess widths/depths, grooves and their positions, screw holes/patterns/pilot depths, supports, terminals, feet and clearances from explicit local and assembly datums. Show relevant front/rear faces, sections and details at legible scales. On-sheet coordinate/hole schedules are acceptable when each feature is keyed to the view. A cut list or unannotated SVG alone is insufficient.

Show recessed-driver seating, compressed seals, remaining wood and the complete fastening stack in section. For purchased ports, show the exact part, mounting pattern, installed length, attachment and dimensioned support/clearance. Preserve factory-pattern accuracy; never round individual factory holes to fit the wood convention. Verification against supplied hardware supplements the dimensioned pattern rather than replacing it. Identify unpublished dimensions and resolve them from reliable evidence where possible; give the exact receiving and fitting action for any remaining interface dimension on the affected drawing. Never supply an invented factory coordinate. Keep precise computational geometry in the project and replay affected simulations after physical changes.

For modular ports, identify the outer flange/flare, cut tube, inner flare and any elbow separately. Draw the outer flange recess when specified, the joint insertion depths, tube cut length, assembled mouth-to-mouth length, and internal protrusion from the finished inside wall. Show both flared ends and distinguish a stock flare contour from an assumed acoustic profile. Never substitute an acoustic effective length or flare correction for a physical cut length. If shortening a tube with an integral flare, mark the unflared end as the cut end. For bent ports, dimension the centreline path, bend radius/angle, orientation, supports and mouth clearances; include their displacement in the net-volume ledger. Where stock insertion dimensions vary, state the final assembled datum that governs and the fit check before bonding.

Keep box and system cutoffs distinct and label their threshold and reference band. Put equal-voltage bass levels beside a plateau-sensitive cutoff and explain whether its change comes from bass output or the midband reference. Distinguish published measurements from quantities derived from digitized reference plots. In the builder document use those physical definitions, not application names or JSON paths.

## Package contents

Write these Markdown files with the images beside them; keep language plain and technical, no chat, no narration of the design history, no first person. Use only the Markdown features the PDF builder supports (headings to level three, paragraphs, lists, pipe tables, images, fenced code, bold, italic, inline code). Keep tables to six columns or fewer so they fit an A4 page.

The cabinet, crossover and performance documents have drawing requirements that the tools do not meet on their own. Add the views and figures needed to satisfy them. Page count and layout are flexible; complete visible dimensions and the required graphs are delivery requirements, not optional illustrations.

The rules below hold for every figure in the package, drawings and plots alike.

**Frequency axes span 20 Hz to 20,000 Hz and use ordinary hertz labels.** Logarithmic spacing is appropriate, but label ticks with numeric frequencies such as 20, 100, 1000 and 20000, never powers of ten or scientific notation. Label the axis with Hz. Show only the supported data range and mark unavailable regions rather than extrapolating limited-band results to fill the axis. Supplementary zoomed views may help explain a feature, but do not replace the full-band plots.

**Required performance graphs:** frequency response (sum and acoustic branches), acoustic phase, spinorama (curve family and directivity indices), excursion, and impedance. Include all five visibly identified graph types, each with the 20–20000 Hz numeric axis above, conditions and legends. Run missing supported analyses before release. Plot the available band and angular coverage accurately; use neutral coverage labels and keep calculation-domain analysis in the evaluation. Never fabricate missing curves. Port speed and other diagnostic figures supplement these required graphs.

**Every figure carries a key, and a style means one thing.** Build the legend from the styles the figure actually drew, so anything a reader can see is named somewhere. Then hold each meaning across the package: settle once what marks material present in this view, a body that belongs to a removed or adjacent sub-assembly but takes up space here, a volume reserved for travel or access, and a feature in a panel seen through the box - and use that same style for that same class in every figure. Solid lines are edges visible in the view; dashed lines are hidden, removed or beyond. One style carrying two meanings in one package misleads more than leaving the feature out would, because nothing tells the reader the meaning changed.

**Absence is not a convention.** Anything that occupies space in a view is drawn in that view, whichever sub-assembly owns it and whether or not it comes away with a panel the view takes off. Leave something out only deliberately, and say so in the caption. A reader cannot tell a part that is not there from a part nobody drew, so an omission that looks like a statement is one.

**The caption carries the view's contract.** The Markdown image text becomes the caption a builder reads under the figure: say what the view is, what was taken away to make it, and what any style means that a builder could not name on sight. A drawing that needs the body text to be understood will be read without it.

1. `README.md`: what the speaker is (topology, drivers, size, mass estimate, sensitivity, impedance, extension), what the package contains, and the specified construction tolerances and assembly instructions.

2. `01-cabinet-construction.md`: materials and panel thickness; outside dimensions; the cut list table; chamber volumes with the accounting (gross, braces, ports, lining, driver displacement, net); panel drawings with cutout positions and diameters for every driver, port and terminal cup; brace positions and window sizes; port tube specification with its length, outer diameter and inner-end clearance, and the interior occupancy table from the candidate notes, so a builder can see what shares the space with what; lining type, thickness and placement; assembly order, gluing and sealing notes; driver mounting hardware from the inventory records; passive radiator tuning mass and adjustment procedure when applicable. Include dimensioned interior views as well as the exterior and panel drawings.

   **The interior has to be visible, not only tabulated.** Draw every compartment, partition, brace and lining region in sections, cutaways or exploded views: compartment dimensions and partition thicknesses; brace position, thickness and window dimensions; lining coverage, thickness and boundaries. Work from shared datums and use enough views to locate every object in all three dimensions, with the clearances and the access a builder needs. Make porous lining visually distinct from solid partitions. The volume accounting and the occupancy table support these drawings and do not replace them. Give a receiving/fit instruction when a factory dimension must be obtained from the supplied part.

3. `02-crossover-construction.md`: the individual-component schematic images; the parts list with value, tolerance, DCR or ESR, voltage or power rating, quantity, vendor and price from the inventory; the connection table (node to node); board placement guidance (coil orientation and spacing, resistor heat, wire gauge from the current figures of `crossover_network` or `board_nodal`); the terminal arrangement, link positions for single-amplifier use and how to remove them for bi-amplification; driver polarity at the terminals; expected component stress with the drive condition that produced it and the frequency of maximum dissipation, each rating quoted with the mounting condition it applies to (free air on the board, not a heatsinked rating), and, where a position dissipates enough to matter, what the builder should expect at sustained level.

   **Every physical part appears once, on its own.** Draw each resistor, capacitor and inductor separately, including each member of a series or parallel bank, with the reference and value that the parts list and the connection table use. Follow a normal IEC or ANSI convention: recognizable symbols, explicit wires, junction dots, unambiguous non-connecting crossings, labelled driver terminals and polarity, and parallel parts on real parallel branches. A box reading "3 in parallel", or one symbol carrying the equivalent value, is not a construction schematic. Split a large network across clearly connected sheets or section views rather than crowding one.

4. `03-performance.md`: the five required graph types; listening geometry; system on-axis response with per-section contributions; acoustic section-phase and relative-phase plots around each crossover; horizontal and vertical maps or selected angles; impedance magnitude and minimum; bass extension figures (f3, f6, f10 with the reference band), excursion and port speed at 2.83 V and at the stress drive, the output limit and its mechanism, naming **which** displacement limit bound and the standard it came from; tolerance envelopes; internal acoustics and panel results for finalists; figure-specific descriptions interpreting the result and its performance or construction implication. Include the spinorama family and directivity indices and explain their listening-window and reflected-sound consequences. Keep orbit completeness and conformance checks in the evaluation. Include a score only when its interpretation adds value. State the operating condition beside every figure.

   **Show the phase that produced the sum, not the filter's.** Plot each section's acoustic phase at one common observation point, including the final crossover transfer, the chosen polarity, the baffle terms and the acoustic offsets that went into the summed response - electrical filter phase is a different curve and does not stand in for it. Around each crossover show the two adjacent sections' relative phase together with their levels and the sum, and mark the acoustic crossing frequency. State the observation axis, the wrapping convention and any common delay removed, and do not shift section delays independently, which hides the relationship the plot exists to show. Then say whether that relationship supports the intended summation across the overlap band: phase agreement is a diagnostic, not a target of zero. Keep reconstruction details in the evaluation. Interpret phase where both branches contribute materially.

5. `04-reference-comparison.md`: side by side, both speakers in every row: dimensions, mass, driver complement, alignment, sensitivity, nominal and minimum impedance, extension, crossover frequencies, power or output rating, price class. The response comparison plot (with comparable voltage, distance and frequency basis, and the reference source) with the octave-band differences and RMS difference. A short reading of where the design approaches, exceeds or falls short of the reference, and what remains unknown about the reference. Compare both speakers in each row using supported quantities. Keep missing-source details in the evaluation and explain any practical consequence without inventing a rating.

6. `05-objectives-and-findings.md`: the objectives table with target, tolerance, result and design response; the unresolved findings that affect construction or use, and the design margins and practical assembly checks that address them. Describe these in terms of the selected speaker; omit iteration budgets, other candidate summaries and framework workflow details.

When room simulations inform the design, include the room geometry, speaker/seat positions, drive condition, direct-versus-reflected response and useful placement range. Use `framework/tools/plot_room_response.py` for a scene/response sheet. Keep room-boundary provenance in the evaluation, distinguish room response from free-field response, and state the placement recommendation and the bass/reflection behavior supporting it.

## Before you finish

Reconstruct every cabinet feature from the drawing dimensions alone. Check the dimension chains for panels, joints, holes, recesses, grooves and installed seal stacks; verify that no adhesive allowance or unspecified fit remains hidden. Inspect the final rendered sheets at their intended print size: every dimension and feature ID must be legible. Confirm all five required graph types and numeric 20–20000 Hz axes. Replace avoidable paragraphs with concise bullets or drawing callouts.

Open every image you generated and check it shows the selected candidate (dimensions, values, curves match `candidate.json` and the result files). Check that the cut list, the drawing, the volume accounting and the `lf_box` net volume agree. Check that the schematic values equal the `crossover_network` parameter file used for the final `whole_speaker` run. Check that the interior views locate every compartment, brace and lining region, that the phase plots explain each crossover, and that every physical part in the parts list can be found in the schematic. A gap in any of those is a document to improve, not a design to reject.

Then check the figures against each other rather than one at a time. Every line style and fill a figure uses is in that figure's key, and the same style means the same thing in every figure of the package. Every occupancy-table entry whose envelope reaches into a view is drawn in that view or accounted for in its caption. Every label the drawing code places is legible in the rendered image: text placed under a patch drawn later vanishes with no warning from the plotting library, so read the PNG, not the script. Finally read each drawing cold and name what every line is without looking at the body text - a line you cannot name is one the builder cannot name either. Read the package once as a builder unfamiliar with the project: remove conversation, and remove anything that only means something inside the framework. Build the PDF with `--preview`, open the page PNGs and check the title page, every drawing page and every table for cut-off content or missing images (the builder also prints a warning for each image it could not find); fix the Markdown and rebuild rather than editing the PDF. Then report to the orchestrator the PDF path and any inconsistency you could not resolve.

## Editorial release check

Read the complete rendered PDF, including text embedded in plots and drawings. Remove every simulation-status disclaimer and generic non-certification statement. Replace bare result narration with useful interpretation. For each performance figure, identify its observed feature, consequence for the speaker and practical implication. Keep real operating constraints and machining instructions; rewrite them as actions rather than disclaimers. Confirm that captions, legends and headings follow the same rule as the prose.
